# 验过的模板

前面九章讲的是方法。这一章给的是真实在跑的系统长什么样——不是为了炫耀，是给你一个"做到什么程度算深度使用"的参照。你可以照着搭，不用一模一样。

## 一个真实系统的样子

下面这套是作者自己日常在用的，数字都是实打实的：

- **41 个仓库**在 GitHub 上跑，Codex 日常负责改写说明、批量处理内容。
- 一份 **859 行**的项目规矩文件（AGENTS.md），里面每一条都来自一次真实事故，不是凭空写的。
- **5 个定时站**每天自动更新不同栏目，有的每天发一条、有的每周汇总。
- **40 多个自建 Skill**，把反复出现的活儿固化成标准流程。

深度用户不是会用多少花哨功能，是把一套自己踩出来的规矩固化下来，让机器每天替你跑。

## 可以直接抄的规矩文件（节选）

下面这段是从真实 AGENTS.md 里抽出来的通用部分，不挑项目，复制进去就能用：

```
1. 回答和文案一律用中文，口语一点，别写成公文。
2. 提到任何文件，写完整路径。
3. 动手之前先说打算怎么做，等我说行再动。
4. 只改我指名的地方，其他一个字都别动。
5. 拿不准的时候停下来问我，不要自己决定。
6. 改完把动过的地方列出来，删掉了什么单独说。
7. 任何表格前后各留一个空行。
8. 新建任何东西之前，先把现有的列一遍，确认没有能用的再建。
9. 链接单独成行，前后留空格，别让括号贴着网址。
```

第 7、8、9 条就是第九章那几个坑的"防法"直接落进文件。规矩和坑是同一件事的两面：坑是教训，规矩是兜底。

## 给 GitHub 仓库的说明模板

如果你也打算把项目放 GitHub 上，仓库首页的说明（README）可以照这个框架写：

```
# 项目名称

一句话说清楚这个仓库是干什么的。

## 它能做什么
- 列三到五条，用大白话说，别写术语。
- 读者一眼看懂"跟我有什么关系"。

## 怎么用
- 第一步：……
- 第二步：……
- 第三步：……

## 背后的规矩
- 这个项目靠一份 AGENTS.md 管着 Codex 怎么干活。
- 列几条最关键的，让看的人知道你不是随便让机器乱跑。

## 适用的人
- 说清楚这份东西是给谁看的，别老少通吃。
```

## 收尾

走到这一步，你已经不是"会用 Codex 的人"，而是"有一套自己系统的人"。手册写到这里，方法都交了。剩下的，是挑一个你真想做的项目，开干，踩坑，然后把坑写进你自己的规矩里。
