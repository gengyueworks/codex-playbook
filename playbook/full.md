## 2. Codex 的执行模型

### 与普通对话工具的本质差异

| 能力维度 | 对话式 AI | Codex |
|---|---|---|
| 项目感知 | 需手动粘贴上下文 | 直接读取项目文件 |
| 代码修改 | 提供建议 | 直接修改并展示 diff |
| 命令执行 | 无法执行 | 可运行构建、测试、部署命令 |
| 任务闭环 | 回答完即结束 | 从理解到交付的完整链路 |

### AI 编程工具的演化路径

| 阶段 | 时间 | 代表 | 核心职责 |
|---|---|---|---|
| 补全 | 2021 | Copilot | 代码补全 |
| 对话 | 2022 | ChatGPT | 代码问答 |
| 协作 | 2023-24 | Cursor | 编辑器内协改 |
| Agent | 2025 | Codex | 端到端任务执行 |

### 非程序员的定位

Codex 的执行模型建立在任务描述和项目上下文之上，而非编程语言知识之上。非程序员的核心能力需求是：

- 清晰定义任务目标与边界
- 准确判断交付结果是否符合预期
- 将重复性任务沉淀为可复用的 Skill 或模板

## 3. AI First 工作习惯

### 核心理念

AI First 不是让 AI 替代判断，而是改变任务的启动方式：**从"先想再做"转为"先让 AI 起头，再逐步收敛"。**

### 五个实践习惯

**① 先让 AI 产生初稿**

适用场景：通知、总结、方案、整理、文档——任何需要从零开始输出的任务。

实践：不要让空白页阻碍行动。AI 的第一版不需要完美，它的核心价值是提供可修改的起点。

**② 提供完整的任务描述**

将"帮我写一下"替换为包含四要素的指令：

```
角色 + 目标 + 上下文约束 + 验收标准
```

详见 [第四章](#4-任务驱动需求表述规范)。

**③ 迭代收敛而非一次到位**

实践模型：

1. 第一轮：获取初稿
2. 第二轮：修正方向（"更短一些""更正式""加入对比表"）
3. 第三轮：细化细节（"检查数据的准确性""移动端是否正常"）
4. 第四轮：最终验收

迭代质量取决于反馈的具体程度。模糊的反馈（"写得不好"）无法指导改进；具体的反馈（"将第一章的对比表改为三列"）让每轮都有明确的收敛方向。

**④ 关键信息必须人工验证**

AI 生成的数据、引用、时间、价格、事实陈述，属于高风险信息类别，不得未经核验直接采纳。验证方式包括：交叉对比原始来源、检查逻辑一致性、在目标环境中实测。

**⑤ 将有效产出沉淀为资产**

| 产出类型 | 沉淀方式 |
|---|---|
| 成功完成的提示词 | 保存为模板文件 |
| 稳定跑通的工作流 | 封装为 Skill |
| 反复遇到的坑 | 写入 AGENTS.md 规则 |
| 有价值的经验 | 记录到本手册 |

### 判断标准

判断是否掌握了 AI First：不是"看过这些原则"，而是下一次遇到新任务时，第一反应是否为**"能不能先让 AI 起个头"。**

## 4. 任务驱动：需求表述规范

### 指令结构

```
角色 + 目标 + 上下文 + 验收标准
```

**示例：**

> 你是前端开发者。优化首页首屏的标题、副标题和 CTA 按钮。
> 项目在 `src/`，使用 React + Tailwind。当前问题：首屏转化率低，用户不清楚产品卖点。
> 验收标准：① 标题表达清晰、② CTA 按钮视觉突出、③ 移动端 375px 下布局正常、④ 不影响其他页面、⑤ 项目可正常构建。

### 边界约束

| 约束类型 | 示例 |
|---|---|
| 文件范围 | 只改 `components/Hero.tsx` 和 `globals.css` |
| 逻辑保护 | 不要修改登录认证流程 |
| 接口保护 | 不要更改 API 请求路径 |
| 依赖保护 | 不要升级或新增依赖包 |
| 页面保护 | 不要影响 `/login` 和 `/settings` 页面 |

缺少边界约束是需求偏移的首要原因。Codex 没有"什么是重要的"这一先验知识，必须显式指定。

### 表述对比

| 模糊表述 | 准确表述 |
|---|---|
| 优化首页 | 优化首页首屏的标题、副标题和 CTA 按钮的文案与样式 |
| 页面不好看 | 调整卡片的间距（从 16px 到 24px）、标题字号（从 18px 到 22px）、按钮颜色（从 #333 到 #0056FF） |
| 登录有问题 | 修复点击登录按钮后页面未跳转的问题（预期：跳转至 `/dashboard`） |
| 做一个后台 | 新增用户列表页，包含：搜索框（按姓名/邮箱）、状态筛选（激活/冻结）、分页（每页 20 条） |

## 5. 标准工作流：需求到交付的六步管控

### 六步流程

| 步骤 | 名称 | 执行内容 | 产出 |
|---|---|---|---|
| 1 | 需求拆解 | 定义背景、问题、范围、边界、标准、风险 | 需求文档 |
| 2 | 制定计划 | 列出执行步骤和涉及文件，确认后再动手 | 执行计划 |
| 3 | 小步实现 | 每次修改一个模块，完成后验证 | 部分交付 |
| 4 | 测试 | 运行自动化测试 + 人工验证关键路径 | 测试报告 |
| 5 | 代码审查 | 审查 diff，确认修改范围与风险 | 审查结论 |
| 6 | 提交复盘 | 提交代码，记录经验，更新规则 | 提交记录 + 经验文档 |

### 需求拆解的六个维度

| 维度 | 要回答的问题 |
|---|---|
| 背景 | 项目当前状态、为何此时修改、任务类型（新功能/修复/优化/重构） |
| 问题定义 | 具体问题、解决程度、排除范围 |
| 文件定位 | 可能涉及的文件清单（先列出，不修改） |
| 边界约束 | 不可修改的模块、接口、页面、依赖 |
| 完成标准 | 可验证的验收条件（需具体、可测试） |
| 风险评估 | 影响范围、样式污染、依赖冲突、兼容性问题 |

完整模板库（含 8 个可直接复制使用的 prompt 模板）见 [workflow.md](workflow.md)。

## 6. 环境配置：Thread、Sandbox、AGENTS.md

### Thread 管理

Thread 是 Codex 中的任务对话单元。设计原则：**一个 Thread 处理一个独立任务。**

| 实践 | 说明 |
|---|---|
| 任务隔离 | 不同任务（新功能/修 bug/优化样式/文档）使用独立 Thread |
| 完成任务归档 | 完成后使用 Archive 清理当前任务列表 |
| 失败任务重开 | 不要在失败的 Thread 上继续，新开 Thread 重新描述需求 |
| 避免上下文膨胀 | 单一 Thread 的对话轮次控制在 20 轮以内 |

**原因**：混合多种任务会导致上下文混乱，降低输出质量，增加审查成本。

### Sandbox 配置

Sandbox 是 Codex 的安全边界。选择原则：

| 配置 | 适用场景 | 风险等级 |
|---|---|---|
| 请求批准 | 日常开发、新手使用 | 低 |
| 自动审批 | 信任已验证的低风险操作 | 中 |
| 完全访问 | 需要系统级操作的自动化任务 | 高 |

**建议**：从"请求批准"开始使用。在确认 Codex 的行为模式可靠后，可根据任务类型调整。

### AGENTS.md

项目根目录下的 `AGENTS.md` 文件用于定义 Codex 的行为规则。Codex 在每次执行任务前自动读取。

**配置示例：**

```markdown
# Project Rules

## Language
- Copy: Chinese
- README: bilingual (zh/en)
- Commit messages: English

## Style
- No AI-generated filler language
- No corporate jargon (赋能, 抓手, 闭环)

## Code
- Never comment out errors to bypass checks
- Verify changes after implementation

## Boundaries
- Do not modify: auth logic, API endpoints, database schema
```

**价值**：消除每次任务中对相同规则的重复描述，降低上下文消耗，确保行为一致性。

## 7. 能力扩展：Skill、Plugin、MCP

### 三者关系

| 概念 | 职责 | 类比 | 使用门槛 |
|---|---|---|---|
| Plugin | 打包 Skill 和 MCP 为可安装单元 | 工具箱 | 普通用户可安装 |

## 8. 实战工作流

### 8.1 写作到仓库

将原创内容转化为开源项目的标准化流程：

1. 完成原创内容的 markdown 文件
2. 使用 Codex 生成项目骨架：README、目录结构、导航索引
3. 组织内容文件到对应的目录结构
4. 生成封面或入口页面（如 `index.html`）
5. 执行 `git push` 发布

### 8.2 内容自动化

使用 GitHub Actions 实现定时更新的标准步骤：

1. 编写 `workflow.yml`：定义触发条件（cron 表达式）和执行步骤
2. 编写更新脚本：生成或更新内容
3. 配置自动提交：在 workflow 中添加 `git add . && git commit && git push`
4. 首次运行后监控：确认 workflow 触发正常、提交正确

### 8.3 批量处理

对多个同类仓库执行统一操作：

1. 定义标准模板（文件结构、内容格式、配置规则）
2. 逐仓库或使用脚本批量应用模板
3. 抽样验证（检查 3-5 个仓库确认应用正确）

### 8.4 数据采集与整理

从外部数据源提取结构化信息的流程：

1. 定位数据源并确认访问方式（API、网页、文件）
2. 编写采集脚本，先在小样本上验证
3. 确认输出格式正确后扩展到全量
4. 结构化保存并沉淀到对应仓库

## 9. 故障排查与方案切换

### 判断框架

当执行路径遇到阻碍时，使用的判断框架：

1. 明确阻碍是**临时性故障**（重试可解决）还是**结构性失效**（方案本身不可行）
2. 如果重试 2-3 次无改善，视为结构性失效
3. 列出替代方案的可行性与代价
4. 优先选择本地化、不依赖外部服务的方案
5. 切换前进行小规模验证，确认新方案可行后再全量执行

### 结构性失效的典型信号

| 信号 | 说明 |
|---|---|
| 连续失败 | 相同操作多次失败且错误信息一致 |
| 服务状态异常 | 页面显示不可恢复的错误或暂停状态 |
| 历史失败率 | 同一服务的历史使用记录多为失败 |

## 10. 进阶用法：超越代码补全

大多数人的用法停留在"打开项目→描述需求→等它改代码"。这当然已经很强，但就像买了一台高性能电脑只拿来看网页——只发挥了 Codex 一小部分能力。本章汇集了从实战中验证过的高级用法，每一项都指向同一个核心：**把 Codex 从"代码生成工具"升级为"长期协作的开发助手"。**

### 10.1 先读项目，再动手

打开一个新项目时，不要直接派任务。先用以下指令建立全局认知：

```
先不要修改任何文件，帮我分析项目结构：
包括技术栈、目录职责、核心模块、启动流程，以及可能存在的问题。
```

这一步相当于让 AI 花少量 Token 画一张地图。后续任务的准确率会明显提升。否则它可能新建重复文件、修改错误模块、破坏原有设计。

### 10.2 先设计方案，再写代码

将单步指令"帮我实现 X"拆为三步：

1. 让它设计方案（列出 2-3 种方案，比较优缺点，不要修改代码）
2. 你选择一个方案并确认
3. 让它按选定方案实现

例如，不要说"增加用户权限系统"，而是：

```
先分析目前权限相关代码，给出 3 种实现方案，比较优缺点，不要修改。
```

确认方案后，再执行：`按方案 2 开始实现`。

原因是：AI 最怕的不是不会写代码，而是不知道你到底想要什么。方案前置让双方对目标有一致理解。

### 10.3 任务拆分：降低 Token 消耗

"帮我重构整个后台"——这句话范围太大，Codex 需要不断读取大量文件，上下文越来越长，Token 自然膨胀。

改为拆分成多个独立任务：

1. 第一轮：分析数据库层的问题
2. 第二轮：优化接口设计
3. 第三轮：重构前端组件
4. 第四轮：补充测试

每轮完成后提交一次，再进入下一轮。不仅省 Token，且每轮的交付质量更稳定。

### 10.4 维护项目专属的 AI 说明文档

Codex 每次进入项目，都像一个新员工——它不知道你的代码习惯、项目规则、命名方式、部署流程。

在项目中维护一个说明文件（如 `PROJECT_CONTEXT.md`），包含：

- 项目介绍与技术栈
- 开发规范与命名约定
- 哪些文件绝对不能修改
- 测试方式与常用命令
- 常见问题与踩坑记录

每次启动任务前，让 Codex 先读这个文件。相当于给 AI 做了一次入职培训，效果非常明显。

### 10.5 用 Codex 做"代码侦探"

线上出现 Bug 时，传统流程是：看日志 → 搜索代码 → 猜问题 → 半天过去。

Codex 可以直接：

```
根据这个错误日志，帮我定位可能的问题路径。不要修改代码，只分析。
```

它经常能快速缩小问题范围，尤其在接手别人遗留项目时，这个能力让排查效率成倍提升。

### 10.6 用 Codex 生成测试

开发者普遍不喜欢写测试——重复、枯燥。但 AI 特别适合这种工作：

```
给这个接口生成完整测试，包括正常情况、异常情况、边界条件。
```

它不会嫌麻烦。让它生成 100 个测试用例，它不会有任何怨言。测试覆盖的价值，往往超过让它多写一个业务功能。

### 10.7 用 Codex 做代码审查

提交代码之前，让 Codex 以审查者视角检查：

- 安全问题
- 性能隐患
- 隐藏的边界 bug
- 是否违反项目规范

很多时候，它发现的潜在问题比自动补全更有价值。

### 10.8 角色模拟：多个视角审查同一段代码

同一个功能完成后，让 Codex 分别扮演不同角色审视输出：

- **产品经理**：从用户体验角度挑问题
- **测试工程师**：找出可能出 Bug 的地方
- **安全工程师**：检查漏洞
- **架构师**：看长期可维护性

用多个视角检查同一段代码，发现的问题比单一视角多一个量级。

### 10.9 每完成一个阶段就提交

AI 写代码最大的风险不是写得慢，而是改得太快——10 分钟改了一堆文件，最后发现方向错了。

- 每完成一个阶段用 Git 提交一次
- 或者让它总结本次修改内容并列出修改文件列表
- 不要让 AI 把整个项目变成你无法追踪的黑盒

### 10.10 Subagent：便宜模型做脏活，主力模型做决策

Codex 的 subagent 机制允许主 Agent（如 GPT 5.6 Sol）与子 Agent 使用不同的模型。例如，可以将 DeepSeek V4 Flash 配置为 subagent 来处理搜索、枚举、资料整理等 Token 密集型任务，让主力模型专注于需要深度推理的决策工作。

关键优势：
- Subagent 拥有独立的 model 和 provider 配置
- 不需要切全局模型，不需要第三方配置切换工具
- 任务传递、工具调用、权限管理仍由 Codex 统一管控
- 大幅度降低 Token 成本

配置完成后，一个任务中两个模型各司其职，成本可控、效率更高。

### 核心理念

Codex 真正改变的不是"程序员不需要写代码了"，而是工作重心的转移：

| | 以前 | 以后 |
|---|---|---|
| 写代码 | 70% | 30% |
| 设计、判断、Review | 30% | 70% |

**Codex 最强的地方不是替你敲键盘，而是把机械性工作拿走，让你把精力放在真正需要判断力的地方。** 如果只是把它当成"帮我生成代码的工具"，只发挥了一小部分能力。真正高级的用法，是把它培养成一个了解你项目、理解你习惯、能够长期协作的开发伙伴。
