# 04 先开对的文件夹，再动手

Codex 能处理很多文件，所以“它能不能做”往往不是最先要问的问题。先确认“它现在看的是哪里、准备动哪里”。

我同步 GitHub 主页数据时，遇到的就是一个很小却很容易出错的任务：主页已经显示 102 个仓库，README 里的徽章还停留在 84。这个任务只需要改三行，前提是不能顺手改掉其他介绍。

## 第一步：让它先读现场

打开正确的项目文件夹后，先说：

```text
请先阅读这个项目的 README 和相关配置，告诉我：
1. 当前显示的仓库数量、公开仓库数量和私有仓库数量分别是什么；
2. 这些数字分别出现在哪些文件和位置；
3. 如果要同步到 GitHub 主页，最小改动会涉及哪些行；
4. 你准备如何确认线上页面已经更新。

现在只读文件，不要修改。
```

这一步能把“我记得是 102”变成“文件里现在写了什么，GitHub 页面实际显示什么”。数字类任务先查证，再改字面，错误会少很多。

## 第二步：限定改动范围

确认结果后，再补一句：

```text
只更新 README 中与仓库数量徽章有关的三行。
保留个人介绍、链接、排版和其他徽章。
修改前先展示拟改内容，修改后列出 diff。
不要提交、不要推送，等我检查后再进行下一步。
```

你可以把“只改三行”写得很具体，也可以直接写“只改这个文件里的这个区块”。范围越清楚，后面的检查越简单。

## 第三步：看改动，不看承诺

Codex 说“已经完成”时，打开改动查看：

```text
请展示本次修改的完整 diff。
请确认除目标三行外，没有其他文件和内容发生变化。
请运行适合这个项目的检查，但不要提交或推送。
```

看到 diff 后，再决定是否提交。推送之后还要打开 GitHub 页面确认，线上结果才是最后一站。

## 关于权限的简单判断

第一次操作一个项目，可以先选择让 Codex 在当前项目文件夹里工作，并保留人工确认。涉及项目外文件、删除、发布、账号权限和网络操作时，先让它说明要做什么，再决定是否放行。

你不用一开始研究所有设置。只记住一条：范围越大、后果越难恢复，确认就要越早发生。

## 常见误区

- 在错误的文件夹里开了对话，Codex 找不到你以为存在的文件。
- 只说“把数据更新一下”，没有说明数据来源和允许修改的位置。
- 看到结果文字正确，就跳过 diff。
- 本地看起来没问题，推送后没有打开线上页面。
