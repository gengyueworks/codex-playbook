# 01 为什么写这本手册

我注册 GitHub 很多年了。

账号一直在那里，想法也一直在那里。真正卡住我的地方很简单：我不会写代码，所以每次想到一个作品，都会在“怎么把它做出来”这里停住。

后来我开始用 Codex。事情慢慢变了。

我还是那个写故事、做内容的人，Codex 负责把一个想法往前推：读文件、整理材料、创建仓库、修改页面、运行检查、把结果留下来。2026 年 8 月，我已经用这套方式维护了 100 多个 GitHub 仓库，里面放着文章、人物故事、音乐和科学内容。

这本手册写给和我一样的人：有想法，有审美，有自己的内容，可一看到文件夹、命令和仓库就容易退缩。

## 我真正学会的第一件事

我以前把 Codex 想成“帮我写几行代码的工具”。这个想法太小了。

我现在更愿意把它当成一个能接住工作的伙伴。你说清楚想做什么，它可以先读一遍现场，再帮你把事情往下推进。你负责判断什么值得做、什么内容是真的、最后交付的样子是否满意。它负责把中间那些麻烦又重复的动作做出来。

举几个我实际做过的例子：

- GitHub 主页显示的仓库数量已经变成 102 个，个人介绍里的徽章还停在 84 个。我让 Codex 先核对真实数据，再只改需要改的三行，最后打开线上页面确认结果。
- 我有 681 条 AI 相关收藏，分布在 32 页里。我让 Codex 先找出分页规律，再逐页整理，最后筛出 22 条真正和 Codex 使用有关的内容。
- 我需要申请 Codex for OSS。Codex 先帮我看清表单字段，再把申请文字压到 500 个字符以内。我一轮轮补充自己的真实经历，最后逐项核对事实。
- 我把一篇篇文章变成公开仓库，再让 GitHub Actions 每天自动更新。作品发布之后，它还会继续长出来。

这些事情的共同点，是我没有先学会编程才开始做。我的工作方式变成了：先把想法说出来，让 Codex 帮我起一个头；看到第一版之后继续挑错；重要事实自己核对；最后把好用的方法留下来。

## 你要负责什么

使用 Codex 的关键，不在于你会多少专业词。

你需要负责四件事：

1. 告诉它你真正想得到的结果。
2. 把能帮助它判断的材料放到手边。
3. 说清楚哪些文件可以改，哪些文件要保留原样。
4. 打开结果看一遍，确认它没有把猜测当成事实。

Codex 可以替你起草、整理、改文件、跑检查。最后要不要发布、这句话是否准确、这个数据能不能公开，仍然由你决定。

## 这本手册怎么读

后面的章节会沿着真实场景往前走：

- 先学会把一句模糊的话说清楚。
- 再让 Codex 读懂你的文件夹和工作习惯。
- 接着把一次好用的操作留下来，变成规则或 Skill。
- 最后让项目自己更新，并学会在失败时把它停下来。

每章都会告诉你三件事：当时要解决什么，具体怎么交代，完成后看哪里。你可以边读边在自己的文件夹里试，不需要先把所有概念学完。

## 现在就做一个小练习

打开一个空白文件，写下下面三句话：

```text
我想让 Codex 帮我完成：
我手边已经有这些材料：
完成后我会通过什么现象判断它做对了：
```

不要急着把它写得漂亮。先选一件你最近真的想做的事，比如整理一次会议记录、把文章放进 GitHub，或者把一批文件改成统一格式。

这三句话写完，你已经拥有了一份可以继续推进的起点。下一章，我们会把它变成 Codex 能够照着执行的交代。
