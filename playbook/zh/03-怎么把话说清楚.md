# 03 怎么把话说清楚

很多人第一次用 Codex，会把一句话直接扔过去：“帮我写一份申请。”

它当然可以写，可它不知道你申请什么、写给谁、哪些事实必须保留，也不知道最后有多少字。于是第一版通常只能算一个起点。

我在准备 Codex for OSS 申请时，走过一遍很典型的过程：先看表单字段，再让 Codex 起草，接着让它指出缺口，我补充自己的经历，最后把每个字段压到 500 个字符以内。

## 先让它指出缺什么

第一轮可以这样交代：

```text
我正在准备一个开源项目申请。

请先不要替我写最终答案。请根据下面的表单要求，告诉我每个字段需要哪些事实、数字和经历。把“必须确认”和“可以后补”分开列出。

限制：每个文字字段不超过 500 个字符，不能编造项目数据，不能把听起来漂亮但无法证明的内容写进去。
```

这一步的价值，在于把你脑子里还没有说清楚的部分暴露出来。比如：项目到底更新了多少次，自动化是否真的运行，作者在其中做了什么，读者能看到什么结果。

## 第二轮补自己的事实

我补充过的事实包括：注册 GitHub 多年但一直不敢动手；自己是文科写作者；用 Codex 维护 100 多个原创内容仓库；有一个项目每天由 GitHub Actions 更新；申请文字需要压到 500 个字符以内。

你可以用这个格式补充：

```text
我的事实如下，请只使用这些信息：
- 我是谁：
- 项目解决什么问题：
- 已经完成的数量和日期：
- 自动化或公开运行的证据：
- 我亲自做了什么：
- 申请额度会用于什么：

请先整理事实表，再告诉我哪些地方仍然缺证据。
```

这里要保留自己的说话方式。申请材料可以更紧凑，经历和语气仍然应该属于你。

## 第三轮让它压缩

等事实确认后，再让它写：

```text
根据已经确认的事实，为三个字段各写一版英文答案。

要求：
1. 每个字段严格少于 500 个字符；
2. 保留非程序员写作者的身份和真实使用过程；
3. 用具体证据替代空泛形容词；
4. 不把我没有说过的数字、项目成绩或影响范围写进去；
5. 输出每个字段的字符数，并标出需要我最终核对的事实。
```

第一版出来以后，继续提出小修改：更像我说话、减少套话、保留“写故事的人在 coder 世界里做作品”这条主线、把弱事实删掉。不要一次把十个要求塞成一团，每轮只解决一类问题，结果更容易判断。

## 最后一轮自己核对

提交前逐项检查：

- 数字是否来自项目文件或 GitHub 页面。
- “每天更新”是否真的有运行记录。
- “原创”是否符合自己的实际情况。
- 字符数是否包含空格和标点。
- 语气是否像自己，读起来是否过度包装。

Codex 能帮你压缩文字，无法替你承担事实责任。表单、申请、合同和公开声明，都要留出这一轮人工确认。

## 一张好用的交代卡

以后写任何重要文案，都可以先填这五行：

```text
我要交付给谁：
我希望对方看完做什么：
必须保留的事实：
明确不能出现的内容：
最终限制：字数、格式、日期或链接要求。
```

这张卡比一条“帮我写得好一点”更有用。它让 Codex 知道结果应该落在哪里，也让你自己知道什么不能让它猜。

## 本章练习

找一个你最近写过的简介、申请、邮件或项目说明，先只写五行交代卡。把它交给 Codex，让它先指出缺口，再开始写。最后保留三份东西：原稿、事实表和最终稿。
