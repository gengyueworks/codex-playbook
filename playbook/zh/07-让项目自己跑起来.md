# 07 让项目自己跑起来

当一个项目每天都要做同一件事，手动操作很快会变成负担。我维护“每天认识一位科学家”项目时，就把每日挑选、归档和展示站重建放进了 GitHub Actions。

这个项目的仓库里有 52 篇人物特写，覆盖 17 个领域。它每天早上自动运行，把当天内容写进 README 和归档，再重建 GitHub Pages 展示站。

## 先把手动流程跑明白

自动化之前，先让 Codex 帮你列出一次手动操作：

```text
请阅读这个项目的 README、data/pool.json、scripts/ 和现有工作流。
请把“每天更新一次内容”拆成一份人工可以完成的步骤清单。
每一步写清输入、输出、失败时会留下什么痕迹。
先不要改文件。
```

如果手动流程都说不清，自动化只会把混乱运行得更快。

## 一个能看懂的工作流

项目里的工作流大致包含这些步骤：

```yaml
name: Daily Update

on:
  schedule:
    - cron: "0 0 * * *"
  workflow_dispatch:

permissions:
  contents: write

jobs:
  update:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - name: Run daily update
        run: python3 scripts/daily_pick.py
      - name: Rebuild site
        run: python3 scripts/build_site.py
      - name: Commit changes when needed
        run: |
          git config user.name "content-bot"
          git config user.email "content-bot@users.noreply.github.com"
          git add -A
          if git diff --cached --quiet; then
            echo "No changes to commit"
          else
            git commit -m "Daily update $(date +%F)"
            git push
          fi
```

这里每一段都有明确作用：什么时候运行、允许写什么、执行哪两个脚本、没有变化时怎样退出。第一次让 Codex 生成工作流时，让它逐行解释，并先用 `workflow_dispatch` 手动跑一遍。

## Codex Automations 和 GitHub Actions

这两个名字都和“定时做事”有关，位置不同：

- Codex Automations 更像你自己的定期提醒或重复任务，重点是让 Codex 按计划回来处理一件事。
- GitHub Actions 住在仓库里，适合构建、检查、更新文件和发布 GitHub Pages。

选择时先看结果要落在哪里。结果要留在 GitHub 仓库并可被别人看到，就优先考虑仓库里的工作流；只是提醒自己处理一项工作，可以从 Codex 的定期任务开始。

## 自动化必须有检查

我会给日更项目加三条护栏：

- 脚本支持手动运行和测试日期，方便补发和排查。
- 没有变化时不提交空 commit。
- 输入数据连续几天没有变化时，标记为需要人工查看，不让系统悄悄失效。

自动化上线后的第一周，每天看一次 Actions 日志。稳定运行一段时间后，也要保留偶尔的抽查。

## 常见故障

- 定时任务没有准点运行：GitHub 的排队时间会波动，先看 Actions 页面，不要只看本地时间。
- 脚本成功但页面没更新：检查是否真的写入文件，以及 Pages 工作流是否完成。
- 每天重复提交同一内容：给脚本加“已有归档就跳过”的判断。
- 任务突然失效：先看最近一次日志、输入文件时间和权限，不要马上重写全部流程。
