# Living Codex Guide Maintenance Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让《非程序员使用 Codex 的经验手册》从一次性成品变成持续吸收真实案例、持续校验、持续发布的长期教程。

**Architecture:** 保留 `playbook/zh/` 和 `playbook/en/` 作为稳定主书；新增 `field-notes/` 承接新案例，新增 `labs/` 承接可运行练习，`docs/` 记录版本、路线图和维护标准。Markdown 仍然是唯一正文来源，在线教程放到后续阶段，避免内容与网站出现两套版本。

**Tech Stack:** GitHub Markdown、GitHub Issues／Discussions、GitHub Actions、Python 标准库、GitHub Pages（后续阶段）。

## 当前基线

- 基线提交：`7a97994`。
- 主书：中文 10 章，英文 10 章。
- 配套资产：双语模板、双语练习、来源说明、案例索引、`scripts/quality_gate.py`。
- 维护原则：Codex 可以协助整理、起草和检查，主线内容由作者审核后进入 `main`。

## 内容分层

```text
稳定主书 playbook/
    解释长期有效的工作方法
        ↓
案例笔记 field-notes/
    记录一次真实操作、一次失败或一次新发现
        ↓
练习 labs/
    把案例变成读者可以运行的脱敏任务
        ↓
模板与规则 templates/、docs/
    把重复判断沉淀成可复用资产
```

主书只在方法发生变化、读者反复卡住或产品能力改变时修改。新案例默认进入 `field-notes/`，避免主书不断变长。

## 内容更新循环

每一篇新内容都按以下顺序完成：

1. **收集问题**：从读者 Issue、对话记录、自己的 Codex 任务和失败日志中选一个具体问题。
2. **确认事实**：记录发生日期、项目类型、输入、实际结果和可公开范围。
3. **跑通案例**：用一份脱敏材料重新走一遍，保存提示词、输出和检查证据。
4. **写中文稿**：按“当时要做什么 → 怎么交代 → 看到了什么 → 哪里出错 → 怎样验收”组织。
5. **制作练习**：抽出公开安全的输入文件，让读者能在 15—30 分钟内完成一次。
6. **补英文稿**：英文版保持相同事实、步骤和验收条件，不追求逐句直译。
7. **接入目录**：更新 README、案例索引、版本说明和必要的内链。
8. **运行门禁**：执行 `python3 scripts/quality_gate.py` 和 `git diff --check`。
9. **人工审阅**：核对事实、隐私、产品版本、链接和作者语气。
10. **小版本发布**：用一条清楚的提交记录说明新增的案例或修正。

## 三阶段路线

### 阶段一：稳定维护，未来 30 天

- 新增 `CONTRIBUTING.md`，说明如何报告过时内容、提交案例和修改翻译。
- 新增 GitHub Issue 模板：内容过时、练习无法运行、链接失效、案例建议。
- 新增 `.github/workflows/quality.yml`，在 Pull Request 和 `main` 推送时运行质量门禁。
- 新增 `docs/路线图.md` 和 `CHANGELOG.md`，记录当前版本、下一个版本和已完成变更。
- 保持主书 10 章不扩张，优先收集读者真实问题。

**阶段验收：** 新贡献者能从 `CONTRIBUTING.md` 找到入口；每个 PR 都自动运行门禁；读者能报告问题；作者能在一个地方看到下一批工作。

### 阶段二：案例生长，未来 2—3 个月

- 建立 `field-notes/zh/` 和 `field-notes/en/`，每篇只讲一个真实场景。
- 首批优先整理已有素材中尚未充分展开的案例：申请表单的多轮核验、转录方案切换、100 多仓库批量维护、日更项目的失败监控。
- 每篇案例配一个 `labs/` 练习，输入材料脱敏，输出结果不预置答案。
- 每月发布 1—2 篇案例笔记；没有真实证据的月份宁可空缺。
- 当同一个问题在 3 个以上案例里重复出现，再把它提炼回主书或模板。

**阶段验收：** 至少 6 篇双语案例笔记、6 个可运行练习；每篇都有来源、日期、失败点、验收清单和英文对应页。

### 阶段三：在线教程，累计 15—20 篇案例后

- 以现有 Markdown 为唯一来源，建立 GitHub Pages 在线阅读站。
- 页面提供章节导航、案例标签、搜索、练习入口和“最后核验日期”。
- 主书、案例、练习和模板互相链接，读者可以按“从零开始”“资料整理”“自动化”“规则与 Skill”四条路线阅读。
- 每次发布由 GitHub Actions 构建站点，并在构建前运行质量门禁。
- 在线站只负责阅读体验，正文仍回到仓库 Markdown 维护。

**阶段验收：** 新读者能从首页开始，完成一个练习，找到对应案例，返回模板，并能看到内容核验日期。

## 维护频率

- 每周：只做素材收集和问题分类，不强行发布。
- 每月：发布 1—2 个真实案例，或完成一次旧章节事实审查。
- 每季度：审查 Codex 产品说明、GitHub Actions 示例、官方链接和过时截图；发布一个小版本。
- 每半年：重新走一遍新手路线，邀请一位没有读过本书的人完成第 02 章练习，记录卡点。

## 贡献和审核规则

- 贡献者提交“问题、案例、练习、翻译、链接修复”中的一种，不接受没有来源的大段泛泛改写。
- 新案例必须包含：背景、输入、交代、结果、失败或限制、验收、来源日期。
- 涉及真实账号、私人数据、未公开项目和付费服务时，先脱敏再进入公开仓库。
- 产品功能、额度、权限和界面描述必须带核验日期，并优先链接官方资料。
- 中文和英文内容一起进入合并流程，缺少对应版本的内容停在草稿区。
- 自动化只负责检查和构建，不自动把 AI 生成正文合并到主线。

## 追踪指标

长期维护看这些信号：

- 新读者是否完成第 02 章练习。
- Issue 中重复出现的问题是否减少。
- 练习失败率和失效链接数量。
- 每篇案例从真实任务到公开发布所需的时间。
- 章节和模板距上次事实核验的天数。
- 中文与英文内容的对应完成率。

星标数量可以观察，但不作为唯一目标。一本经验手册的生命力，首先体现在读者能否拿它完成一件事。

## 不进入主线的内容

- 没有真实操作记录的泛泛技巧。
- 无法核验来源的产品结论。
- 只有漂亮截图、缺少输入和结果的演示。
- 包含私人信息、账号、密钥或无法公开的工作材料。
- 只改变措辞、没有增加读者行动价值的重复文章。
